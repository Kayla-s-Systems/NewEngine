# Code of Conduct

## Our Pledge

We are committed to making the CoreEngine / NewEngine community a professional, respectful, and technically focused environment.

This project is built around clear architectural boundaries, replaceable providers, explicit contracts, and long-term maintainability. We expect the same clarity and respect in communication, collaboration, reviews, issues, pull requests, documentation, and technical decisions.

## Our Standards

Examples of behavior that helps the project:

- Respectful and constructive technical discussion.
- Clear reasoning when proposing architectural or API changes.
- Honest reporting of bugs, regressions, limitations, and technical debt.
- Respect for maintainers, contributors, plugin authors, tool developers, artists, and documentation writers.
- Preference for explicit contracts over hidden behavior.
- Preference for clean, maintainable solutions over quick hacks.
- Keeping discussions focused on the project, its architecture, tooling, runtime systems, plugins, and content pipeline.

Examples of unacceptable behavior:

- Harassment, threats, insults, personal attacks, or targeted hostility.
- Discrimination or exclusionary behavior.
- Trolling, repeated disruption, or bad-faith participation.
- Publishing private information without permission.
- Dismissing contributors based on background, experience level, language, location, or identity.
- Pressuring maintainers to merge unsafe, unreviewed, or architecture-breaking changes.
- Introducing hidden fallbacks, legacy aliases, provider-specific shortcuts, or undocumented behavior while representing them as stable design.
- Abusing issue trackers, discussions, pull requests, or review channels.

## Technical Integrity

CoreEngine / NewEngine values technical integrity.

Contributors are expected to respect the project architecture:

- Consumers should use engine-facing gateway contracts.
- Providers should declare their services and capabilities explicitly.
- Runtime code should not depend on concrete backend implementations.
- Plugin identity should come from descriptors and metadata, not filenames.
- Hidden in-process fallback backends and undocumented compatibility shims should not be introduced.
- Breaking changes must be clearly documented.
- Known limitations should be stated honestly.

Technical disagreement is welcome. Personal hostility is not.

## Scope

This Code of Conduct applies to all project spaces, including:

- Repository issues and pull requests.
- Discussions, comments, reviews, and documentation.
- Project websites, knowledge bases, and community channels.
- Plugin, tooling, importer, codec, renderer, physics, asset, and runtime contributions.
- Public representation of the project when acting as a contributor or maintainer.
